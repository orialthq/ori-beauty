# 계획

저장해둔 것을 필요한 순간에 다시 꺼내기 위한 예약이다. 맛집 기능이 아니라 앱이
저장한 것 전부에 걸린다.

정리함은 폴더가 아니라 태그로 정리한다. 계획이 "어디서 찾을까"를 물을 때
고르는 것도 태그이고, 고른 태그 중 **하나라도** 붙은 것이 검색 대상이 된다.

## 이 폴더

| 문서 | 다루는 것 |
|---|---|
| **README** (여기) | 계획 전체의 틀, 세 성격, 순서 |
| [RECOMMENDATION](RECOMMENDATION.md) | 추천 — 저장한 것 중 하나를 고르는 판단. 모든 성격이 공유한다 |
| [PLACE_TYPE](PLACE_TYPE.md) | 장소형 — 좌표, 지오펜스, 근처 알림 |

물건형과 행위형은 아직 문서가 없다. 장소형을 먼저 세우고 그때 나눈다.

## 계획의 세 가지 성격

같은 계획이지만 무엇을 예약하느냐에 따라 상황의 모양이 다르다.

| 성격 | 카테고리 | 상황을 이루는 것 | 근처 알림 |
|---|---|---|---|
| **장소형** | 맛집·카페, 여행·장소, 뷰티숍 | 언제 + 어디서 | 성립 |
| **물건형** | 쇼핑, 뷰티 제품, 영양제 | 언제 살지, 언제 떨어지는지 | 매장 앞 정도 |
| **행위형** | 레시피, 운동, 생활·팁 | 언제, 어떤 맥락에서 | 성립 안 함 |

지금 계획 만들기 화면은 시간 · 장소 · 둘 다 세 가지를 받는다. 이것으로
**장소형과 행위형은 이미 표현된다.** 행위형은 시간만 쓰면 되고, "주말에 이
레시피 해보기"는 지금 화면으로 그대로 만들어진다.

물건형이 애매하다. "언제 떨어지는지"는 시각이 아니라 소진 예측이라 사용자가
날짜를 직접 잡아야 한다. 당분간 그대로 두고, 물건형을 제대로 다룰 때 다시 본다.

**만드는 순서는 장소형부터**다. 다만 설계는 처음부터 카테고리 중립으로 잡는다.
나중에 넓히려고 뜯어고치는 것보다 싸다.

## 이미 있는 것

코드에서 확인한 것들이다. 생각보다 많이 서 있다.

| 조각 | 코드 |
|---|---|
| 캡처 여러 장 가져오기 | 인앱 피커 |
| 캡처 읽어 분류·장소 뽑기 | `/v1/analyze`, gpt-5.6-luna |
| **언제 · 어디 받기** | **`PlanDraft.scheduledAt` + `locationQuery`** |
| 계획 저장·수정·일시정지 | `PlanController` |
| 시각·위치에 알림 띄우기 | 트리거 네이티브 (iOS 1274줄 / Android 20여 파일) |
| 알림에서 원본 캡처 열기 | `home_shell` ← `triggerOpened` |
| 결과 묻기 | `home_shell` 다녀왔어요 / 안 갔어요 / 아직 몰라요 |

배달 인프라는 다 있다. 배달할 물건이 없을 뿐이다.

## 없는 것 — 추천

계획을 저장하면 사용자가 적은 제목이 그대로 알림 문구가 된다. 저장한 것을
들여다보지 않는다.

우리가 하려는 두 가지가 공유하는 조각이 정확히 이것 하나다.

```
계획 (언제·어디)  →  ???  →  알림  →  결과 확인
                    추천
```

1. 계획이 스스로 무엇을 꺼낼지 고른다
2. 그 앞을 지나갈 때 꺼낸다

가운데를 한 번 만들면 둘이 같이 쓴다. 설계는 [RECOMMENDATION](RECOMMENDATION.md)에 있다.

## 순서

**1. 추천 만들기** — 두 기능의 심장. 화면은 건드리지 않고 결과만 확인한다.
장소형으로 먼저 재되, 행위형도 같은 호출로 되는지 함께 본다.
→ [RECOMMENDATION](RECOMMENDATION.md)

**2. 계획함에 붙이기** — 이것이 이 기능의 본체다.

사용자가 계획을 적으면 **그 자리에서 바로** 저장한 것 중 맞는 것을 보여준다.
알림을 기다릴 필요가 없다. "성수 저녁 약속"이라고 적으면 저장해둔 곳 중
성수에서 갈 만한 한 곳과 대안 둘이 그 화면에 나온다.

알림은 그 다음이다. 계획 시각이 되면 이미 고른 것을 꺼내 보여준다.

새 화면은 필요 없다. 계획 편집 화면과 계획함 카드에 자리를 만들면 된다.

여기까지 하면 핵심 가설을 측정할 수 있다.

**3. 좌표 채우기** — 근처 알림에만 필요하다. → [PLACE_TYPE](PLACE_TYPE.md)

**4. 근처 알림에 붙이기** — 3번이 끝나야 시작할 수 있다. 네이티브는 이미 있다.
→ [PLACE_TYPE](PLACE_TYPE.md)

1·2번은 좌표가 전혀 필요 없다. 지도·길찾기·공유가 지금도 좌표 없이 도는 것과
같은 이유다. 좌표는 지오펜스 하나 때문에 필요하고, 그것도 OS 기본 지오코더로
채울 수 있는지 먼저 잰다.

## 측정

- 계획에서 추천을 받은 비율 — 맞는 것이 있었는가
- 추천 이후 행동 실행률 — 장소형은 지도·길찾기·공유, 물건형은 구매 링크
- 저장했던 것의 확인된 사용률 — 방문했는가, 샀는가, 해봤는가
- 두 번째 계획에서 다시 쓰는 비율

결과는 이미 만들어진 3버튼이 받는다. 지금은 계획 알림에 매달려 있는데, 추천이
생기면 원래 물어야 할 대상 — 추천한 것을 실제로 했는지 — 에 붙는다.

문구는 성격에 따라 달라져야 한다. "다녀왔어요"는 장소형 말이고, 쇼핑이면
"샀어요", 레시피면 "해봤어요"가 맞다.

## 볼트와의 차이

기획 볼트(`assets/오리알트/`)는 전부 맛집 전제로 쓰여 있다. `domain: dining`,
`ENT-001 식당 지점`, `CTX-001 식사 상황`, `DEC-001 이번 식사 결정`.

이 폴더는 그보다 넓다. 볼트는 당분간 그대로 두고 맛집을 첫 사례로 검증한다.
동작하는 것을 본 뒤에 일반화하는 편이 순서상 안전하다.

대응 관계만 적어둔다. 나중에 볼트를 넓힐 때 출발점이 된다.

| 볼트 (맛집) | 이 폴더 (일반) |
|---|---|
| DAT-001 맛집 캡처 | 저장한 캡처 |
| ENT-001 식당 지점 | 저장한 대상 |
| CTX-001 식사 상황 | 계획 — 언제·어디·무엇 |
| DEC-001 이번 식사 결정 | 추천 |
| ACT-001 지도·예약·공유 | 대상별 행동 |
| OUT-001 방문 결과 | 사용 결과 |

볼트의 `DEC-002_근처 알림 여부`가 비어 있는 것도 그대로다.
[PLACE_TYPE](PLACE_TYPE.md)의 알림 규칙이 그 자리를 채울 내용이다.

## 아직 정하지 않은 것

- **물건형의 상황 표현.** "언제 떨어지는지"를 지금 UI로는 받을 수 없다
- 성격별로 나뉘는 것들은 각 문서에 적어둔다
