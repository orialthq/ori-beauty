# 태깅 — 쓰던 말을 다시 쓰게 만드는 하네스

캡처 하나가 들어왔을 때 어떤 태그를 어떻게 붙이는지, 그 주변에 무엇을 세워
두었는지, 무엇을 재는지의 기록입니다. 모델 호출 자체는 한 단계이고, 나머지가
전부 하네스입니다.

## 태그가 하는 일

사람이 뭔가를 캡처하는 순간은 "나중에 이거 찾고 싶다"는 순간이고, 나중에
남는 것은 캡처가 아니라 몇 개의 단어입니다 — 을지로, 닭발, 웨이팅 있던 데.
태그는 그 단어를 미리 붙여 두는 것이라, 좋은 태그의 기준은 하나입니다.
**나중에 그 말로 찾았을 때 나오는가.**

거기서 나오는 원칙 여섯 개가 아래 구조 하나씩에 대응합니다.

| 원칙 | 무엇이 그것을 지키나 |
|---|---|
| 1. 이미 쓰던 말로 부른다 | 요청에 어휘를 실어 보냄 · 표기 키로 합침 |
| 2. 맞는 말은 전부 붙인다 | 평평한 저장 (`f9171a7`) |
| 3. 빠뜨리지 않는다 | 칸을 나눠 묻고 평평하게 저장 |
| 4. 근거 없으면 안 붙인다 | 관찰 먼저 · 근거 표시 · 확인 권장 표시 |
| 5. 사람이 고친 건 최종이다 | `source: user`는 어떤 패스도 건드리지 않음 |
| 6. 재본다 | 평가 도구의 태그 검사·재현성·어휘 건강 |

## 흐름

```
앱      정리함의 태그 어휘 (이름·횟수, 최대 300)  ─┐
                                                 ├→ POST /v1/analyze
앱      스크린샷                                  ─┘
서버    [1] 칸 나눠 묻기   filing.fields / areas / kinds / traits
        [2] 평평하게      tags[] + facet, 슬롯 순서대로
        [3] 표기 합치기   tagKey 같으면 하나, 어휘의 표기로 고쳐 씀
        [4] 근거 수리     없는 evidence id 잘라내고 needs_review
앱      [5] 표기 합치기   정리함의 표기로 한 번 더 (마지막 방어선)
앱      [6] 확인 화면     태그 ← "읽은 말", 약한 태그는 ? 표시
앱      [7] 사서 패스     모든 태그 화면에서 "이 둘은 하나" 제안
```

### 어휘를 보낸다 (원칙 1)

`멕시코 음식`과 `멕시코음식`이 갈라지는 이유는 모델이 틀려서가 아니라 두
번째 캡처를 태깅할 때 첫 번째가 뭐라고 불렸는지 모르기 때문입니다. 그래서
분석 요청에 정리함의 태그 목록이 `이름(횟수)`로 함께 갑니다
(`RemoteContentAnalysisService.vocabulary`). 프롬프트의 규칙은 하나입니다:
맞는 기존 태그가 있으면 그 표기 그대로 쓰고, 어떤 것도 맞지 않을 때만 새
단어를 만든다. 목록에 있다는 이유만으로 고르지는 않는다.

보내는 것은 단어와 횟수뿐입니다. 어떤 캡처에 어떤 단어가 붙어 있는지는
모델이 알 필요가 없고 알지 못합니다. 300개에서 자르는 이유는 그 뒤가 한 번
쓰인 긴 꼬리라 유도할 값어치가 가장 낮은 단어들이기 때문입니다.

### 표기는 코드가 합친다 (원칙 1)

띄어쓰기·구분자·대소문자 차이는 판단이 아니라 표기입니다. `tagKey`
([lib/domain/tag_key.dart](../lib/domain/tag_key.dart), 서버의
`src/tag_key.js`와 같은 정의)는 공백과 태그 알파벳의 구분자
`· ㆍ & / + ~ -`를 전부 지우고 소문자로 만든 것이고, 키가 같으면 같은
태그입니다. 표시 이름은 **정리함이 이미 쓰던 표기**가 이깁니다.

- 서버: 한 응답 안에서 키 중복을 걷어내고, 요청의 어휘와 키가 같으면 어휘의
  표기로 고쳐 씁니다.
- 앱: 분석 결과, 웹 보강 태그, 사용자가 확인 화면에서 단 태그, 이름 바꾸기
  — 태그가 들어오는 모든 길목에서 `adoptedSpellings`로 정리함의 표기를
  입힙니다. 예전 스냅샷은 복원할 때 한 번 훑어 합칩니다(`_unifySpellings`).
- 이름 바꾸기에서 같은 단어의 다른 표기를 적으면 그것만은 적은 대로
  갑니다. 그 요청은 "이 말을 이렇게 쓰겠다" 말고 다른 뜻일 수 없습니다.

`카페`와 `커피숍`은 키가 다릅니다. 동의어는 판단이고, 코드에 동의어 사전을
두기 시작하면 폴더 체계가 사전의 모습으로 돌아옵니다. 그 판단은 어휘를 본
모델([사서 패스](#사서-패스가-제안한다-원칙-1-5))과 사용자의 몫입니다.

### 칸을 나눠 묻고 평평하게 둔다 (원칙 3)

모델에게 "맞는 단어 다 적어라"고만 하면 어떤 캡처는 동네를 빼먹고 어떤
캡처는 특성만 셋씩 답니다. 스키마가 네 칸으로 묻습니다.

| 칸 | 묻는 것 | 값 |
|---|---|---|
| `fields` | 어느 생활 영역인가 | **닫힘**: 뷰티, 건강·운동, 맛집·카페, 레시피, 장소, 생활·팁 |
| `areas` | 어디인가 | 열림. `place.searchArea`와 같은 표기 |
| `kinds` | 무엇인가 | 열림. 넓고 재사용되는 말을 우선 |
| `traits` | 어떤 성질인가 | 열림. 화면에 보일 때만 |

[PLACE_ENRICHMENT.md](PLACE_ENRICHMENT.md)가 잰 결론이 그대로입니다 — 값을
닫으면 재현성 9/10, 열어두면 4/10. 세상이 작은 칸(`fields`)만 닫습니다.
`traits`를 닫지 않은 것은 뷰티·레시피까지 걸치는 특성 목록을 데이터 없이
지어낼 수 없어서이고, 어휘 건강 수치가 쌓이면 다시 봅니다.

#### 값을 닫는 것과 경계를 긋는 것은 다른 일이다

이 칸은 원래 `여행·장소`였고, `여행` 쪽이 문제였습니다. 어디든 누군가는
여행 가는 곳이라, 그 말은 모든 식당에 스스로 따라붙었습니다. 실제 장소 캡처
4장을 4번씩 돌려 재보니 맛집·카페는 16/16인데 `여행·장소`는 12/16 — 같은
스크린샷에서 네 장 모두가 붙었다 안 붙었다 했습니다. 세 번에 한 번 빠지는
태그는 판단이 아니라 동전 던지기이고, 거의 모든 장소에 붙는 말은
`단체 가능` 10/10과 같아서 아무 장소도 가려내지 못합니다.

목록을 닫아도 **어느 값을 언제 쓸지**는 정해지지 않는다는 게 배운 것입니다.
그래서 이름을 `장소`로 두고 프롬프트에 경계를 적었습니다 — 먹거나 마시러
가는 곳은 맛집·카페 하나뿐, 그 밖의 이유로 가는 곳(관광지·숙소·전시·공연·
체험·공원·서점)은 장소, 한 캡처가 둘 다 갖지 않습니다. 고친 뒤 다시 재니
식당 4장은 맛집·카페 16/16에 장소 0/16, 음식 아닌 장소 3장은 장소 9/9에
맛집·카페 0/9였습니다. 규칙 문구는 `analysis_schema.test.js`가 붙잡습니다.

#### 한 칸은 한 질문만 답한다

`쇼핑`도 같은 이유로 뺐습니다. 나머지가 **어느 영역인가**를 답할 때 그것만
**그걸 어쩔 건가(살 것)**를 답해서, 가려내는 대신 위에 얹혔습니다. 올리브영
캡처는 3/3으로 뷰티이면서 쇼핑이었습니다.

여행과 달리 쇼핑은 흔들리지 않았고(구매 캡처 9/9), 그래서 빼는 데에는 아는
값을 치릅니다 — 가전이나 패션 구매 캡처는 이제 영역이 **아예 없습니다**.
받아 줄 다른 말이 목록에 없기 때문입니다. 그 캡처들은 `kinds`의 가전·패션과
검색으로 찾고, "내 삶의 어느 영역인가"에는 답하지 않습니다. 빈 `fields`는
실패가 아니라 정답이라고 프롬프트에 적어 두었습니다.

빼고 나서 잰 값이 그 자리에 함정이 하나 더 있다고 알려줬습니다. 갈 곳을 잃은
가전·패션 캡처가 **생활·팁으로 6번 중 4번 흘러들었습니다.** 빈칸이 정답이라고
적어 둔 것만으로는 부족했고, 모델은 남는 칸을 만능칸으로 씁니다. 그래서
생활·팁이 무엇인지를 적었습니다 — 청소·정리·수납·세탁·수리처럼 **하는** 일이지
**사는** 일이 아니며, 아무 영역에도 안 맞는 캡처를 담는 자리가 아니라고. 다시
재니 가전·패션은 6/6으로 영역 없음, 올리브영은 3/3 뷰티 하나였습니다.

세 번 다 같은 교훈입니다. 한 칸이 두 질문을 받으면 값들이 서로 겹치고, 값 하나를
빼면 남은 값 중 가장 헐거운 것이 그 자리를 대신 받습니다. 그래서 뺄 때마다 다시
재야 합니다.

저장은 여전히 평평합니다. 서버가 네 칸을 `tags[]`로 펴고 각 태그에 `facet`
(`field | area | kind | trait`)을 `source`처럼 얹을 뿐, 위아래는 없습니다.
사용자가 단 태그에는 facet이 없고 아무것도 그것을 필요로 하지 않습니다.
분석 스키마 버전은 `2.1`입니다.

### 근거를 보여주고 약한 태그를 표시한다 (원칙 4)

태그는 스크린샷에 대한 주장이고, 읽은 말이 있어야 확인할 수 있습니다.
확인 화면의 태그 편집기는 칩 아래에 `성수 ← "성수동 2가"`를 그립니다.
프롬프트는 상호명이나 인테리어만 근거인 태그를 0.4 이하로 두라고 하므로,
`confidence < 0.5`인 분석 태그는 약한 것으로 보고 `?`를 붙입니다
(`ContentTag.isWeak`). 지우지는 않습니다 — 사용자가 볼 수 있는 짐작은 빈칸보다
낫고, 남길지는 사용자가 정합니다.

서버는 태그의 `evidenceIds`도 제목·장소·사실과 같은 방식으로 수리합니다.
없는 id를 가리키면 잘라내고 `needs_review`로 내립니다.

### 사서 패스가 제안한다 (원칙 1, 5)

`POST /v1/tag-merges`는 어휘 전체를 받아 "이 둘은 하나"인 쌍을 돌려줍니다.
키가 같은 쌍은 코드가 먼저 짝짓고, 나머지는 모델이 봅니다 — 뜻이 같은 다른
말(`피부관리`/`스킨케어`)만, 층위가 다른 것(`뷰티`/`스킨케어`)이나 관련만
있는 것(`을지로`/`종로`)은 아닙니다. 서버는 두 이름이 어휘에 있는지, 적게
쓰인 쪽이 많이 쓰인 쪽으로 가는지 확인합니다.

`모든 태그` 화면이 그 쌍을 맨 위에 보여주고, 합치기는 사용자가 누릅니다.
합쳐진 태그는 `source: user`가 되고, 그 뒤로 어떤 패스도 그것을 고치지
않습니다. 어휘 전달이 잘 되면 이 패스가 할 일이 거의 없어야 정상입니다.

## 연상어 사전 — 태그 이름이 아니라 하고 싶은 말로 찾기

별자리 검색창에 "매운거 먹고 싶어"라고 치면 닭발이 추천되는 것은 검색
순간의 모델 호출이 아니라 **미리 만들어 둔 사전**입니다. 업계 관행
(DoorDash의 오프라인 배치 질의 이해, doc2query 계열의 문서 쪽 확장,
Algolia의 1-way synonym)이 전부 이 방향입니다 — 키 입력 경로에는 문자열
대조만 두고, 뜻 판단은 태그가 생길 때 한 번만.

```
[백그라운드 — 태그가 새로 생길 때만]
어휘의 새 태그 → POST /v1/tag-senses → 태그마다 연상어 ≤8개
  닭발 → 매운, 야식, 술안주        (1-way: 이 말들이 닭발로 이어질 뿐,
  을지로 → (없음, 빈 목록도 답)      닭발이 다른 태그로 번지지 않는다)
→ 스냅샷 v5의 tagSenses에 저장. 한 태그는 평생 한 번만 묻는다

[타이핑 — 호출 0, <1ms]
"매운거" → 양방향 prefix 매칭(매운거 ↔ 매운)  ← 어미·조사 룰 대신
이름 매칭은 부분 문자열 + 초성(ㄷㅂ → 닭발)
걸린 태그: 하늘에서 중간 밝기 + 검색창 밑에 `닭발 ← 매운` 칩
칩 탭 = 그 말을 태그로 바꿔 진짜 검색. 확정은 언제나 사용자
칩 길게 누르기 = 그 연상어를 사전에서 빼기. 뺀 것은 다시 오지 않는다
```

지킨 규칙: 방향은 한쪽뿐(태그 이름은 절대 확장되지 않음), 목록은 태그당
8개 이하, 형태 변이는 목록이 아니라 매칭(양방향 prefix·초성)으로, 승인은
사람(칩이 왜 걸렸는지 말하고, 틀리면 빼게). 서버가 응답에서 다른 태그의
이름을 연상어로 쓰는 것을 걷어내고, 요청에 없던 태그의 답을 버립니다.

## 재는 것 (원칙 6)

`tool/evals`가 분류 pass/fail에 더해 다음을 냅니다.
자세한 사용법은 [tool/evals/README.md](../tool/evals/README.md)에 있습니다.

- **정확도** — manifest의 `expectedTags`/`forbiddenTags`를 `tagKey`로 대조.
  재현율은 게이트, 정밀도는 숫자만 (어휘는 자라야 하니 맞는 태그가 하나 더
  붙은 것은 실패가 아님)
- **재현성** — `--repeat N`으로 같은 캡처를 N번 돌려 태그 집합의 Jaccard
- **어휘 건강** — 서로 다른 키 수, 한 번만 쓰인 키의 비율, 캡처당 태그 수,
  **한 키에 표기가 둘 이상인 수**(`spellingVariants`), 약한 태그 수
- **어휘의 효과** — `--vocabulary`로 어휘를 보내고, `--grow-vocabulary`로
  실행 순서대로 라이브러리가 자라는 것을 흉내 냄. "쓰던 말을 다시 쓰는가"의
  직접 검사

아직 없는 숫자: 실제 홀드아웃 17장에 기대 태그를 달아 돌린 기준선. 이
문서의 구조가 효과가 있었는지는 그 숫자가 말합니다.

## 정한 것과 열어둔 것

- `traits` 닫힌 목록은 지어내지 않았다. 어휘 건강 수치를 보고 정한다.
- 약한 태그의 선 `0.5`는 프롬프트가 스스로 정한 `≤ 0.4` 계약에서 온다.
- 어휘 상한 300은 요청 크기와 긴 꼬리의 값어치로 정했고 재보지 않았다.
- 사서 패스의 결과를 사용자가 얼마나 받아들이는지가 이 패스의 실체다.
