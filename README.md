# Trun On

> 캡처를 쓸모로.

Trun On은 SNS에서 발견해 캡처하거나 공유한 정보를 원본 근거와 함께 이해하고
정리해, 사용자가 필요한 순간 다시 쓸 수 있게 만드는 서비스입니다. 현재는
화면에 실제로 보이는 정보만 구조화하는 Android-first Flutter 앱으로
베이스라인을 검증하고 있습니다.

현재 음식·레시피 캡처를 첫 실제 이미지 입력군으로 검증하면서 기존
뷰티 텍스트 흐름도 유지합니다. 구매 추천이나 활용 단계로 바로 넘어가지
않고 `input → 분석 → 확인 → 정리` 베이스라인의 정확도에 집중합니다.

## 현재 흐름

```text
SNS에서 이미지·URL·텍스트 공유
→ 원본과 수집 시점 보존
→ 콘텐츠 유형 분류
→ 재료·순서·상품 정보·리뷰·비교와 근거 추출
→ 누락·충돌·불확실한 결과 확인
→ 정리함에 보관
```

이미지 분석 결과는 다음 유형 중 하나입니다.

- 뷰티 제품
- 레시피
- 소스·양념 레시피
- 상품
- 제품 리뷰
- 메뉴 비교
- 분류 불가

레시피에는 재료 그룹과 조리 순서, 그 외 콘텐츠에는 화면에서 확인한
사실을 저장합니다. 제목·분량·단위·순서가 보이지 않으면 만들지 않고
누락으로 남기며, 서로 다른 값이 보이면 충돌로 표시합니다. 각 결과는
이미지에서 읽은 짧은 근거를 참조합니다.

정리함은 콘텐츠를 태그로 정리합니다. 폴더와 하위 분류의 위계는 없고, 캡처
하나에 `맛집·카페`, `국밥`, `을지로`, `웨이팅`처럼 맞는 말이 전부 나란히
붙습니다. 올리브영에서 산 화장품이 뷰티이면서 쇼핑인 것을 폴더 하나로는
표현할 수 없었기 때문입니다.

각 태그는 화면 어디에서 읽었는지와, AI·사용자·웹 중 어디서 왔는지를 함께
들고 다닙니다. 사용자는 확인 화면에서 태그를 달고 떼고 고칠 수 있으며, 그렇게
바꾼 것은 출처가 사용자로 남습니다. 브랜드나 개별 게시물 이름처럼 이 캡처
하나에만 붙을 말은 태그로 만들지 않고, 화면에서 근거를 찾지 못하면 태그를
붙이지 않습니다. 태그가 하나도 없는 캡처는 정리함이 따로 모아 보여줍니다.

태그는 분류가 아니라 나중의 내가 찾을 때 쓸 낱말이라, 새로 짓기보다 쓰던
말을 다시 씁니다. 분석 요청에는 정리함이 이미 쓰는 태그 목록이 함께 가고,
모델은 맞는 말이 있으면 그 표기 그대로 씁니다. `스킨케어`와 `스킨 케어`처럼
표기만 다른 것은 들어오는 길에 하나로 합쳐지고, `멕시코 음식`과 `멕시칸`처럼
뜻이 같은 다른 말은 `모든 태그` 화면이 제안만 하고 합치는 것은 사용자가
합니다. 어떻게 묻고 무엇을 재는지는 [태깅](docs/TAGGING.md)에 있습니다.

## 제품 원칙

1. **분석보다 보존** — 분석이 실패해도 공유한 원본은 남습니다.
2. **결론보다 근거** — 구조화된 값은 확인 가능한 원본 근거를 가집니다.
3. **확정 대신 불확실성** — 모르는 값과 단위를 임의로 채우지 않습니다.
4. **자동화보다 사용자 통제** — 사용자가 확인한 뒤에만 정리 완료됩니다.
5. **앱 UI와 콘텐츠 구분** — 좋아요 수, 댓글 수, 캐러셀 번호 같은 SNS
   UI를 레시피 값으로 취급하지 않습니다.
6. **개인정보 최소화** — 계정명, 얼굴, 댓글 작성자, 통화 정보는 분석
   결과에 넣지 않습니다.

## 로컬 실행

필수 환경:

- Flutter `3.44.8`
- Dart `3.12.2`
- Android Studio와 Android SDK
- Node.js 20 이상
- macOS Keychain service `ori-beauty-openai`, account `ori-beauty`에
  저장된 OpenAI API 키

키체인 식별자는 기존 로컬 개발 환경과의 호환을 위해 현재 이름을 유지합니다.

먼저 로컬 분석 서버를 실행합니다.

```bash
cd server
npm run dev
```

다른 터미널에서 앱을 실행합니다.

```bash
flutter pub get
flutter analyze --fatal-infos
flutter test
flutter run
```

Android 에뮬레이터는 기본적으로 호스트 서버를
`http://10.0.2.2:8787`에서 찾습니다. 실제 Android 기기는 USB 연결 후:

```bash
adb reverse tcp:8787 tcp:8787
flutter run --dart-define=ORI_ANALYSIS_BASE_URL=http://127.0.0.1:8787
```

OpenAI 키는 Flutter 앱, APK, 저장소에 포함되지 않습니다. 로컬 서버는
`gpt-5.6-luna`, 이미지 `detail: original`, strict Structured Outputs,
`store: false`를 사용하며 키·이미지·모델 응답 본문을 로그에 남기지
않습니다. 운영 배포에는 별도의 인증·TLS·요청 제한 계층이 필요합니다.

## 구현된 베이스라인

- Android `text/plain`, JPEG, PNG, WebP 공유 수신
- Galaxy 캡처 미리보기의 이미지 `열기` 후보 등록·자동 가져오기
- 캡처 수신 직후 분석 상태 카드와 알림 권한 허용 시 앱 복귀 알림
- 다른 기본 이미지 앱과 무관하게 동작하는 `Trun On에 추가` 빠른 설정 타일
- 앱 시작 전에도 공유를 잃지 않는 pending queue
- MIME·magic bytes·크기·해상도 검증
- app-private 파일 복사, flush, atomic rename
- 분석용 임시 원본과 정리함의 durable 원본 수명 분리
- snapshot 저장 성공 뒤에만 pending 공유 acknowledge
- 앱 재시작 후 분석 결과 복원으로 불필요한 API 재호출 방지
- Luna 이미지 분석과 서버·클라이언트 양쪽의 strict schema 검증
- 근거 ID의 중복과 잘못된 참조 거부
- 레시피·상품·리뷰·비교에 맞춘 검토 화면
- Luna의 태그 생성과 정리함의 태그별 보기·사용자 편집
- 태그마다 화면 근거와 출처(AI·사용자·웹) 기록
- 기존 뷰티 텍스트 정규화·제품 확인·제품 묶음 유지

현재 이미지는 한 장씩 분석합니다. 여러 장을 한 번에 공유하면 일부를
조용히 버리지 않고 지원되지 않는 입력으로 표시합니다.

## 비공개 실측

실제 SNS 캡처 17장은 개인정보와 저작권이 포함된 비공개 holdout으로만
로컬 평가하며 저장소에 커밋하지 않습니다. 추적되는 manifest에는
`holdout-01` 같은 불투명 ID와 기대 분류만 남습니다.

```bash
dart run tool/evals/run_local_eval.dart
```

평가 결과에도 원문·이미지·계정명·모델 응답은 기록하지 않고 분류별
pass/fail 집계만 남깁니다.

## 이번 단계에서 하지 않는 것

- 구매 후보·보류·제외 결정
- 제품이나 메뉴의 추천 순위
- 가격·최저가·재고·구매 링크·알림
- 성분 안전성·효능 검증·의학적 판단
- 광고 여부 추론 또는 크리에이터 신뢰 점수
- 플랫폼 제한을 우회하는 크롤링이나 영상 다운로드
- 커뮤니티·댓글·팔로우
- Android 베이스라인 검증 전 iOS 동시 출시

세부 범위는 [제품 정의](docs/PRODUCT.md), 구현 계약은
[아키텍처](docs/ARCHITECTURE.md), 진행 계획은
[베이스라인 로드맵](docs/ROADMAP.md)을 참고하세요. iOS 팀원은
[iOS 실행 가이드](docs/IOS_TEAMMATE_GUIDE.md)에서 현재 지원 범위와 실행 방법을
확인할 수 있습니다. 맛집·카페 축을 어떻게 정했고 어떤 측정을 근거로 삼았는지는
[장소 보강](docs/PLACE_ENRICHMENT.md)에 있습니다.
